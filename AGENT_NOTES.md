# Agent Notes — eBay Scheduled Listings: SVG/Style Refresh

Notes for whichever Claude session picks this up next (possibly on a different
machine). Written 2026-09-27 after refreshing the logo SVG + `<style>` blocks
across all scheduled `tcg_gems` eBay listings.

## What the task was

The `tcg_gems` eBay account had 6 scheduled listings whose description HTML
was originally generated by this app's "Copy Style & HTML" button. After
recent fixes to the logo (`fix thick blue letter outline`, `fix excess vertical spacing around logo`), the already-created listings still had the
**old** SVG + CSS baked into their descriptions. Task: swap in the new
SVG + `<style>` blocks on all 6 listings, without touching anything else
(title, description paragraphs, packaging/shipping sections).

## Key structural fact (still true unless App.module.scss / Logo change again)

A listing description generated by this app has this exact shape:

```
<style>...</style>   (7 style tags back to back, from every imported .module.scss)
<div class="App_ebayListing__JZWOi">      <- outer wrapper, DO NOT TOUCH
  <div class="Logo_wrapper__aH5ni">        <- Logo block — this + the 7 style
    <svg>...</svg>                            tags are the ONLY things to replace
  </div>
  <h1 class="App_h1__I1N+d ...">TITLE</h1>  <- per-listing, DO NOT TOUCH
  ...rest of listing (description/packaging/shipping)... <- DO NOT TOUCH
</div>
```

The class hashes (`App_ebayListing__JZWOi`, `Logo_wrapper__aH5ni`, etc.) are
CSS-module content hashes — they only change if the corresponding
`.module.scss` file's content changes. As of this session they matched
exactly between a fresh `localhost:3000` generation and the old listings, so
the untouched HTML (h1, wrapper div) kept working with the new CSS without
modification.

**Reliable boundary marker:** search the raw HTML for the first
`</svg></div>` — everything from index 0 up to (and including) that string is
"style + logo" and safe to replace wholesale. Everything after it (starting
with `<h1`) is per-listing content and must be preserved byte-for-byte.

## How to (re)generate the new style+SVG content

1. Open `http://localhost:3000/` (run `npm start` first if not already running).
2. Click the account matching the eBay seller (`Omar` → `tcg_gems`, `Ammi` →
   `poke_gems`, `Soukayna` → `poke_relics`).
3. Type any placeholder title (e.g. "Placeholder") and click **Generate**
   (calls the AI backend — needs `server/server.js` running and an OpenAI key
   in `.env`).
4. Once the preview renders, click **Copy Style & HTML**. This copies
   `<style>×7 tags> + <the full rendered div>` to the system clipboard.

That clipboard content is identical for every listing under the same
account — generate it once, reuse for every listing.

## THE BIG GOTCHA: eBay's Revise form ignores scripted textarea edits

eBay's "Revise your listing" → Description → "Show HTML code" reveals a real
`<textarea name="description">`. It is tempting to just do:

```js
nativeSetter.call(textarea, newValue);
textarea.dispatchEvent(new Event('input', { bubbles: true }));
```

**This does not work**, even though:

- the WYSIWYG preview updates correctly afterward,
- clicking Save shows "Your listing has been revised" with no error.

Reload the revise page fresh afterward and the old content is still there —
nothing was actually saved. Confirmed this is not a caching issue; it's that
eBay's save pipeline only picks up changes that come from **genuine
browser-level input events** (real keystrokes / real paste), not
programmatically dispatched ones. A tiny real-`type()`-driven edit persisted
immediately; the identical edit done via `textarea.value =` + dispatchEvent
did not, even though both fire `input`/`change`.

**Lesson: any edit to this textarea must be done via genuine simulated
keyboard input (the `computer` tool's `type`/`key` actions), never via
`element.value =` + dispatched events, or it silently won't save.**

## The method that actually works (validated, used for all 6 listings)

Per listing:

1. Navigate to `https://www.ebay.co.uk/lstng?mode=ReviseItem&itemId=<id>`.
2. Find and click the "Show HTML code" checkbox (usually needs **two**
   clicks — the first often doesn't register, the second does; verify by
   reading the checkbox / textarea class afterward, since the textarea has
   `class="se-rte__button-group-editor__html hidden"` when the box is
   unchecked, and loses `hidden` once actually checked — it is _not_
   focusable/typeable while hidden).
3. Once genuinely visible, use JS (read-only + selection state, no value
   mutation) to select exactly the region to replace:
   ```js
   const ta = document.querySelector('textarea[name="description"]');
   const v = ta.value;
   const idx = v.indexOf('</svg></div>') + '</svg></div>'.length;
   ta.focus();
   ta.setSelectionRange(0, idx);
   ```
   (Setting `selectionStart`/`selectionEnd` programmatically is fine — it's
   only the _value_ mutation that eBay ignores. A real keystroke that then
   acts on that selection is treated as genuine.)
4. Use the `computer` tool's `type` action (real simulated typing, not JS)
   to type the replacement: first the 7 `<style>` blocks, then
   `<div class="App_ebayListing__JZWOi">`, in one `type` call; then a second
   `type` call for `<div class="Logo_wrapper__...">...</svg></div>`. (Split
   into two calls just because it's long — one call also works.) Typing
   replaces the selected range exactly like a real user pasting/typing over
   a selection.
5. Verify via read-only JS: check the new length, that
   `v.includes('<svg width="1552" height="387"')`, and that the tail of the
   string (packaging/shipping text) is unchanged.
6. Click **Save** (find via `Array.from(document.querySelectorAll('button')).find(b => /^save$/i.test(b.textContent.trim()))`
   — the button only appears/enables after a real edit is registered; on a
   pristine page load only "Preview" is present). Confirm the "Your listing
   has been revised" dialog, click Done.
7. **Always re-navigate to the same revise URL fresh afterward and check
   `textarea.value` again** to confirm persistence before moving to the next
   listing. Don't trust the success dialog alone (see gotcha above).

## Things that wasted time and should be skipped next time

- **Don't bother with clipboard `Cmd+V`** as a transport between the
  localhost:3000 tab and the eBay tab. It worked maybe 1 time in 3 with no
  discernible pattern (possibly tied to OS-level window focus, which this
  automation doesn't control). Faster path: read the style/svg content once
  into the agent's own context (small enough — ~21KB total), then embed it
  literally in each `computer.type` call. No clipboard needed at all.
- `navigator.clipboard.writeText()` / `.readText()` called from injected
  page JS (not from a real click handler) hangs indefinitely (45s+ timeout)
  — presumably an invisible permission prompt automation can't dismiss.
  Only a genuine user-gesture-triggered click on the app's own "Copy Style &
  HTML" button reliably writes to the clipboard.
- The "Show HTML code" checkbox visually not toggling on the first click is
  normal here — just click again and confirm via screenshot/class check
  before proceeding.
- Downloading a file via a Blob URL + synthetic `<a>` click works fine and
  lands in `~/Downloads` (as a temporary dot-prefixed filename until
  Chrome finalizes it) — a viable way to get large data out of a page
  without the clipboard, if ever needed again.
